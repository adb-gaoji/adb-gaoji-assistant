# 新手任务清单（good first issue 候选项）

这些任务**都不碰手机写入、不涉及危险操作**，改坏了 CI 会立刻告诉你。
适合第一次参与本项目。

挑中一个之后：

1. 在对应的 Issue 下留言说要接，避免多人重复
2. 从 `main` 拉分支
3. 改完跑 `npm test` 和 `npm run ci`
4. 提 PR，模板里有检查清单

有疑问直接在 Issue 里问，或者去 [Discussions](https://github.com/adb-gaoji/adb-gaoji-assistant/discussions)。

---

## 一、重构类（纯内部改动，行为不变，测试兜底）

### 1. 拆分 `renderer.js`

**现状**：`src/renderer.js` 83.6 KB / 1681 行，设备、应用、存储、投屏、
谷歌三件套、主题、日志全在一个文件里。改一处要翻很久，合并冲突也频繁。

**目标**：按功能域拆成若干模块。渲染进程是普通 `<script>` 加载（不是 bundler），
所以拆法要适配——可以先按 IIFE 挂到 `window.gaojiXxx` 命名空间，
或者评估引入轻量打包。

**怎么算完成**：
- `npm test` 55 项全绿
- `npm run audit:ui-state` 与 `npm run audit:themes` 通过
- `npm start` 手工过一遍主要页面，行为与拆分前一致

**难度**：⭐⭐⭐　**这是价值最高的一个**，做完后面的改动都会轻松很多。

---

### 2. 统一动作分发路径

**现状**：`src/main.js` 有一个处理 28 个私有动作的 `switch`，
`src/action_handlers.js` 有 110 个动作的 handler 表——**两套并行**。
新增动作时要判断该放哪边，容易放错。

**目标**：合并成一个分发入口，或者明确划出「为什么这两类必须分开」并通过注释与测试固化下来。

**怎么算完成**：
- `npm run audit:actions` 返回 0
- 110 个动作全部仍能正确路由（现有测试会验证）
- `CONTRIBUTING.md` 的「新增动作」章节同步更新

**难度**：⭐⭐⭐

---

### 3. 把审计脚本的重复逻辑抽出来

**现状**：`scripts/` 下有 9 个审计脚本，各自都写了「读源文件 → 正则校验 →
收集 findings → 按退出码返回」这套骨架，重复度不低。

**目标**：抽一个共享的小工具，让每个审计只写自己那部分规则。

**注意**：**不要改动退出码语义**——`2` = P0 必修、`1` = 已登记的 P1 缺口、
`0` = 通过。CI 靠它区分「已知缺口」和「新引入的问题」。

**难度**：⭐⭐

---

## 二、功能类（有明确边界，不碰危险操作）

### 4. 任务取消

**现状**：任务中心只能等任务跑完，中途想停没有办法。
`npm run audit:tasks` 已经把这个标为已知缺口（P1），CI 会以警告形式提示。

**目标**：给长任务加取消能力，取消后状态正确、资源释放干净。

**怎么算完成**：
- `audit:tasks` 不再报这条 P1
- 新增测试覆盖「取消中」「已取消」状态转换
- 取消后不残留子进程

**难度**：⭐⭐⭐

---

### 5. 操作历史界面化

**现状**：每次操作都写进 `action-history.jsonl`，但**没有界面能查**。
数据早就在那了，缺个入口。

**目标**：做一个可查询、可筛选的操作历史页面。

**难度**：⭐⭐

---

### 6. 新增界面风格

**现状**：已有 6 套主题，加第 7 套是很好的入门任务。

**怎么做**：
1. 照着 [`design/README.md`](../design/README.md) 在 `src/styles.css` 加一组
   `:root[data-theme="你的id"]` CSS 变量
2. 在 `src/renderer.js` 的 `THEMES` 数组里注册（id / 名称 / 图标 / 明暗）
3. **必须**跑通 `npm run audit:contrast`——它用真实渲染测量 6 处文字
   在每套主题下的 WCAG 对比度，达不到 4.5 就报错
4. 附一张 `design/app/<id>.png` 截图

**难度**：⭐⭐　**最适合第一次提 PR**。

---

### 7. 完善机型兼容性列表

**现状**：README 里有机型适配表格，但覆盖的机型有限。

**怎么做**：用 [机型实测反馈](https://github.com/adb-gaoji/adb-gaoji-assistant/issues/new?template=device_report.yml)
提交你手上机型的实测结果。**失败的记录同样有价值**。

如果你愿意，也可以把多条实测记录整理进 README 的兼容性表格。

**难度**：⭐　**不需要写代码**。

---

## 三、文档与文案类

### 8. 校对中文文案

**现状**：界面和文档全部中文，但难免有用词不一致、表意含糊的地方。

**目标**：指出并修正不准确、有误导或前后不一致的文案。

**要求**：改动要能说明**为什么原文不好**，而不只是换个说法。

**难度**：⭐

---

### 9. 补充某机型的刷机说明

如果你成功用本工具刷过某个机型，把过程写成一份说明文档很有价值——
比如「刷完首次开机要等 5 分钟属于正常」这类经验。

**难度**：⭐⭐

---

## 四、工程类

### 10. 按需下载低频工具

**现状**：`resources/bundled-tools/` 占 117 MB（QPST、FreeControl、驱动安装器），
但多数用户用不到，却要一直背着这 117 MB。

**目标**：改为首次使用时下载，并做好校验与失败提示。

**注意**：要保留「离线可用」这个核心优势——至少要有手动放置文件的路径。

**难度**：⭐⭐⭐

---

### 11. 评估 Electron 主版本升级

**现状**：`electron` / `electron-builder` 构建链有 16 项开发依赖告警
（生产依赖 0 漏洞）。修复需要从 Electron 41 升到 44，属于跨主版本。

**目标**：先做影响评估（哪些 API 变化、回归面多大），再决定是否升。

**难度**：⭐⭐⭐

---

## 从哪开始？

- **完全没写过 Electron**：选 6（新增主题）或 8（校对文案）
- **会前端**：选 5（操作历史界面）或 6
- **会 Node**：选 3（审计脚本去重）或 2（统一分发）
- **想啃硬骨头**：选 1（拆 renderer.js）——收益最大

不确定的话，在 [Discussions](https://github.com/adb-gaoji/adb-gaoji-assistant/discussions)
里说一句你的背景，我们帮你挑一个。
