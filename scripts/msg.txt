fix(flash): 刷机失败不再报成功，并让过程实时可见

三个会导致"刷机失败却显示成功"或"刷机卡住"的问题。

1) 刷机失败可能显示成功（两个独立原因）

   a) runProcess 用 `code ?? 0` 收尾。进程被异常终止时 code 为 null，
      被当成 0（成功）。真机验证：kill 掉 fastboot 后
      close 事件为 code=null / signal=SIGTERM，旧写法判定为成功。
      刷机中途数据线松脱就会走这条路径。

   b) fastboot 的失败经常不体现在退出码上。下面这些输出伴随的
      退出码可能是 0：
        Sending 'boot_a' (65536 KB) FAILED!
        FAILED (remote: 'unknown partition')
        fastboot: error: cannot load 'boot.img'
      只看退出码会把失败当成功。

   现改为同时检查退出码与输出内容。

2) 刷机中途会卡住不动

   刷机命令完全没有超时保护。设备掉线时 fastboot 打印
   `< waiting for any device >` 后永久挂起（真机实测：5 秒后仍未结束，
   必须强制终止）。旧代码因此会一直卡在"刷机中"。
   现按镜像体积计算超时，超时即终止并报告。

3) reboot-bootloader 之后命令必定失败

   设备重启回 Fastboot 需十几秒，期间命令只能得到 Device not found。
   现主动等待设备回归（最多 90 秒）再继续。

另外：传输层抖动（写入失败、设备掉线、超时）自动重试一次；
分区名错、镜像缺失这类重试无用的问题不重试，直接说明原因。

刷机过程实时可见

此前详细输出只进底部日志面板，刷机时要切页面再滚动才看得到。
现「固件刷机」页面直接显示进度条、第 N/共 M 条计数、当前命令、
每条 fastboot 原始输出、结束统计（成功/失败/跳过/用时），
失败时指出第几步及原因。

用结构化 flash-progress IPC 事件而非让前端解析日志字符串，
日志格式调整时界面不会跟着失效。

判定策略

  flash / erase / set-active 失败 -> 立即中止
    （继续可能造成分区与启动槽不一致）
  getvar / reboot 失败 -> 不中止
    （官方 XML 常用 getvar 校验，变量不存在不代表刷机有问题）

新增 src/flash_runner.js：命令分类、超时计算、成功失败判定、
重试策略的纯函数实现。

验证

- CI 15 项全绿。

  据此固定"异常终止必须判失败"的不变量。
- 界面验证：离屏渲染确认进度 UI 正确，并修掉进度条比计数滞后一格。
